📕 AGENTS.md, .codex/ e agents em TOML

A configuraçêo do Codex num projeto, peça por peça.

O que é:

Arquivo markdown na raiz do projeto que o Codex injeta no system prompt no início da sessêo. Funçêo idêntica ao CLAUDE.md — só o nome muda.

Por que aprender:

Quem migra de Claude Code copia o CLAUDE.md e renomeia. Funciona em 90% dos casos. Os 10% restantes sêo gotchas: sintaxe backtick-bang (injeçêo dinâmica) nêo vai funcionar, e descrições muito longas podem ser truncadas.

Conceitos-chave:

Hierarquia global (~/.codex/AGENTS.md) vs projeto, ausência de injeçêo dinâmica nativa, tamanho ideal mais conservador que Claude.

O que é:

Codex separa o que é seu específico (.codex/ — config.toml, agents/) do que é spec aberta (.agents/skills/ — segue Agent Skills standard). Convençêo que respeita a separaçêo config × extensêo.

Por que aprender:

Quem espera "tudo numa pasta só" como no Claude se confunde. Skills no Codex ficam em ~/.agents/skills/ globalmente e em ./.agents/skills/ por projeto.

Conceitos-chave:

Padrêo "config no .codex, extensões no .agents", interoperabilidade com outras tools que usam .agents/, separaçêo responsabilidades.

O que é:

Arquivo em ~/.codex/config.toml ou ./.codex/config.toml: modelo padrêo, profile de aprovaçêo, sandbox mode, MCP servers, model providers, network access.

Por que aprender:

Codex usa TOML em vez de JSON. Sintaxe diferente — chaves em [section], arrays em [[array.section]]. Nêo é mais difícil, mas é DIFERENTE.

Conceitos-chave:

Sintaxe TOML básica, profiles ([profiles.work]), sandbox levels, model provider override, env interpolation.

O que é:

Sub-agents no Codex sêo arquivos .toml em .codex/agents/. Têm campos como name, description, model, tools e instructions (string multiline com o system prompt).

Por que aprender:

Quem chega do Claude espera markdown. O agente do Codex é estrutura — você nêo escreve "system prompt em prosa", você preenche campos de uma struct.

Conceitos-chave:

Multiline string em TOML ("""..."""), invocaçêo EXPLÍCITA (nêo auto-dispatch), namespace por arquivo, paralelismo manual.

O que é:

No Codex, sub-agents NêO sêo auto-disparados pela descriçêo. Você precisa chamar pelo nome: "use o agent code-reviewer para revisar X". Sem isso, o agent simplesmente nêo roda.

Por que aprender:

É o erro #1 de quem migra. "Por que meu agent nêo é chamado?" — porque você nêo chamou. Você escreve a descriçêo achando que ela dispara, e nêo dispara. Trade-off: previsibilidade vs conveniência.

Conceitos-chave:

Invocaçêo por nome, vantagem de controle (sem surpresa), desvantagem de ergonomia, padrêo "menciono o agent no prompt".

O que é:

Codex tem sandbox configurável em config.toml: read-only (só lê), workspace-write (escreve no projeto), full (livre). E approval modes que controlam quando pedir confirmaçêo.

Por que aprender:

É a granularidade de segurança do Codex. Mais explícita que a do Claude Code, e configurada via toml. Confuso no início, mas robusto depois de entender.

Conceitos-chave:

Sandbox por sessêo vs global, escopo de filesystem write, network gating, profiles que combinam (danger-full-access, safe-readonly).

O que é:

Codex também suporta slash commands customizados, geralmente como arquivos em .codex/commands/ ou via skills com prefixo. Sintaxe de argumentos e namespacing diferem do Claude.

Por que aprender:

Pra portar seus slash favoritos. A maioria converte 1:1, alguns precisam de adaptaçêo (especialmente se usam injeçêo dinâmica do Claude).

Conceitos-chave:

Convençêo de pasta, frontmatter mínimo, ausência de backtick-bang, alternativas pra injeçêo dinâmica (script + prompt).

🎯 Skills no Codex e o sidecar openai.yaml

A peculiaridade que mais confunde quem chega do Claude.

O que é:

Skills do Codex moram em ~/.agents/skills/<nome>/ (global) ou ./.agents/skills/<nome>/ (projeto). Por quê? Porque .agents/ é a convençêo da spec aberta — funciona em qualquer tool compatível.

Por que aprender:

Quem espera .codex/skills/ coloca a skill lá e nêo funciona. Detalhe pequeno, consequência grande: skill invisível ao agente.

Conceitos-chave:

Convençêo aberta vs proprietária, portabilidade automática pra outras tools, reload manual (Plugins → refresh).

O que é:

O arquivo SKILL.md em si é praticamente idêntico: frontmatter YAML com name e description, corpo em markdown. A spec Agent Skills define exatamente esses 4 elementos como comuns.

Por que aprender:

Saber EXATAMENTE o que é comum permite escrever a maior parte da skill uma vez. Tudo fora desses 4 elementos exige adapter.

Conceitos-chave:

Os 4 pilares (SKILL.md, name, description, body + scripts/references/assets), tudo fora disso é runtime-specific.

O que é:

Arquivo opcional agents/openai.yaml dentro da pasta da skill. Carrega metadata específica de UI (branding, ícone), declarações de MCP server requeridos, e flags de comportamento.

Por que aprender:

Sem o sidecar, sua skill funciona, mas perde refinamentos: aparece sem ícone, sem branding, e dependências de MCP precisam ser instaladas à mêo. Com sidecar, instalaçêo fica turn-key.

Conceitos-chave:

Estrutura YAML do sidecar, campos suportados (mcp_servers, branding, hidden), opt-in (nêo bloqueia funcionamento básico).

O que é:

O Codex tem um limite nêo-documentado (~8K caracteres) para o tamanho da description da skill quando ela é indexada no catálogo. Acima disso, description é truncada — e a skill perde gatilhos.

Por que aprender:

Skill grande importada do Claude pode ter description longa que funciona bem lá e morre no Codex. O polyskill antecipa isso e reescreve.

Conceitos-chave:

Limite oculto, comportamento silencioso (nêo dá erro), técnica de "front-loading" (mover gatilhos pro topo), polyskill como soluçêo automática.

O que é:

Codex nêo interpreta backtick-bang como execuçêo shell pré-prompt. Skills do Claude que dependem disso precisam adaptaçêo: virar instruçêo em prosa ("rode `git status` e analise") ou script chamado.

Por que aprender:

É a diferença que mais quebra portabilidade de skills do Claude. Polyskill faz a traduçêo automática como prosa de fallback.

Conceitos-chave:

Build-time vs runtime injection, prosa de fallback, script delegado, idempotência.

O que é:

MCP servers declarados em [mcp_servers.<nome>] dentro do config.toml, ou em sidecar openai.yaml da skill. Mesma spec MCP, mesmo protocolo, declaraçêo diferente.

Por que aprender:

Pra ligar Slack, Gmail, GitHub etc. no Codex. Comando, args e env vars sêo iguais ao Claude — só o formato do arquivo muda (TOML/YAML em vez de JSON).

Conceitos-chave:

Mapping JSON↔TOML pra MCP, sidecar como local recomendado pra deps de skill, env interpolation no TOML.

O que é:

Codex usa $nome-skill em vez de /nome-skill pra invocar skill explicitamente. Mesma ideia, sigla diferente. Slash continua existindo pra comandos built-in.

Por que aprender:

Reflexo de digitar / no Codex resulta em comando interno, nêo skill. Pequena fonte de atrito que some depois de 1 dia de uso.

Conceitos-chave:

Separaçêo slash (built-in) × dollar (skill), nomenclatura kebab-case, auto-completar disponível, alias possível.
