📋 Session handoff — the standardized summary

A short, structured summary you ask the current agent for BEFORE handing things off to the other one. This is the feature that unlocks a dual workflow. Without it, you keep re-explaining context. With it, you have a cheat sheet and can move on.

Handoff template (5 sections)

# Session handoff — 2026-05-24 16:30

## 🎯 Foco atual
Implementar autenticaçêo OAuth no /api/auth com Google.

## 📂 Arquivos tocados (com estado)
- src/api/auth.ts          ← parcial, falta validaçêo JWT
- src/api/auth.test.ts     ← testes do happy path passando
- prisma/schema.prisma     ← adicionou model OAuthAccount

## ✅ Decisões tomadas
- Usar passport.js (nêo auth0)
- JWT em cookie httpOnly (nêo localStorage)
- Refresh token rotacionando a cada 1h

## 🚧 Problema aberto
JWT verification falhando com "jwt malformed" no payload de teste.
Tentei 3 abordagens (recriar token, mudar secret, verificar
cookie parse) sem sucesso. Provável bug na lib ou no setup do test.

## ⏭ Próximos passos
1. Investigar setup do test (jest mock do passport?)
2. Se persistir, trocar passport por jose lib
3. Implementar refresh endpoint
4. Cobertura de erro paths

✓ Good handoff

  • • Short (fits on one page)
  • • Fixed structure (5 sections)
  • • List of files WITH status
  • • Explicit decisions (not obvious from the code)
  • • Current problem with previous attempts

✗ Useless handoff

  • • "I'm working on feature X" (vague)
  • • 20 pages of context (no one reads them)
  • • No current problem (doesn't know what to do)
  • • Decisions you can read from the code (redundant)
  • • No next step

💡Becomes a skill

Perfect candidate for a skill session-handoff in both runtimes (written once via polyskill). You run /session-handoff or $session-handoff, gets the completed template ready to paste into the other agent.

🖥️ Two terminals, one project — VS Code setup

Practical setup that works: VS Code open in the project, two terminal panes — one running claude, another running codex. Same filesystem, same git, same docs. You switch panels with a shortcut.

⚠️ Avoiding conflicts — when both edit

If both agents edit the same file at the same time, one overrides the other. It’s the #1 way to lose work with a dual workflow. The solution is simple discipline: split by area or phase.

📂 Division by area

Each agent works in different folders:

Claude   → src/api/    (backend)
Codex    → src/ui/     (frontend)

No overlap, no conflicts. Simpler.

⚙️ Division by phase

Same area, different phases:

Claude   → implementa src/x.ts
Codex    → escreve testes/x.test.ts

Coordinates: implementation done? Tell Codex to run a test.

Advanced strategies

Git branch per agent: claude works in feat/x-impl, codex in feat/x-test. Merge later.
Manual lock via comment: whoever gets there first adds it // LOCKED by claude — 16:30 at the top. Someone else sees it and respects it.
git stash between switches: before switching agents, stash any partial work. The other agent works in a clean state.

⚠️The scenario to avoid

Two agents editing src/api/auth.ts in parallel. Claude finishes and writes. Codex finishes 30s later and writes over it—Claude’s work is lost. You discover at the next commit that half the changes are missing. 1–2 hours of drama to reconstruct it.

🔌 Shared MCP servers

MCP servers run as independent processes. Configured once, both agents connect to the same. The server isn’t duplicated—only the declaration on the client (JSON for Claude, TOML for Codex).

Mirrored configuration

# Claude: .mcp.json (no projeto)
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@mcp/github"],
      "env": { "TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}

# Codex: .codex/config.toml (no projeto)
[mcp_servers.github]
command = "npx"
args = ["-y", "@mcp/github"]

[mcp_servers.github.env]
TOKEN = "${GITHUB_TOKEN}"

# Resultado:
# Os dois agentes apontam pro MESMO server (mesmo binário,
# mesmas credenciais, mesmas ferramentas expostas).
🔧

Independent server

MCP server is a process. It starts when called and stays available. It doesn't matter who called it.

🔑

Centralized env

Use .env shared. The GitHub token is in one place — both clients read it.

🛡️

Allowlist by runtime

Each client can have a different allowlist. Codex allows everything, Claude allows read-only access. OK.

💡Maintenance

A skill that needs a specific MCP? Declare it in openai.yaml sidecar for Codex AND in the frontmatter or doc for Claude. Polyskill handles this automatically when building.

🪝 Hooks shared via script

Hooks are shell commands. Put the logic in scripts/check.sh in the project, both runtimes point to this script. Maintenance in one place—edit the script, and both agents follow it.

Recommended standard

# scripts/lint-on-edit.sh — lógica central
#!/bin/bash
set -e

CHANGED_FILE="$1"  # passado pelo hook

if [[ "$CHANGED_FILE" == *.ts ]]; then
  npx tsc --noEmit "$CHANGED_FILE"
  npx eslint "$CHANGED_FILE"
fi

if [[ "$CHANGED_FILE" == *.py ]]; then
  ruff check "$CHANGED_FILE"
fi

# .claude/settings.json — declara o hook
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit",
      "hooks": [{
        "type": "command",
        "command": "./scripts/lint-on-edit.sh ${file}"
      }]
    }]
  }
}

# .codex/config.toml — mesma coisa
[[hooks]]
event = "post_tool_use"
matcher = "edit"
command = "./scripts/lint-on-edit.sh ${file}"

✓ Logic in the script

  • • Update the script → applies to both
  • • Script can be tested outside the agent
  • • Versioned alongside the code
  • • Can also be used in CI/pre-commit

✗ Inline logic in hooks

  • • Duplicates regex/commands across both runtimes
  • • Forgets to update one side
  • • Hard to test in isolation
  • • Can't be reused outside hooks

💡Git pre-commit hook too

Put scripts/lint-on-edit.sh no .git/hooks/pre-commit (or via husky). The same logic applies to both agents and manual commits. Triple guarantee.

📝

Write in CLAUDE.md/AGENTS.md

Put the rule in the project manual. Everyone on the team sees it.

🔬

Periodic A/B testing

Every 2–3 months, redo a task in both. Calibrate the rule.

🎲

"Grab the idle one"

When it's a tie, use whichever has less context loaded.

💡Quarterly review

Models are updated all the time. What was one model’s strength may be another model’s strength 3 months later. Schedule a review of the rule of thumb every quarter. Without a review, the rule becomes a myth.

How to contribute a new adapter

  1. Repo fork linnoff88-dev/pollyskill
  2. Create a new file in src/adapters/<nome>.ts implementing an interface Adapter (parse, emit, validate)
  3. Register in src/adapters/index.ts: register(new SeuAdapter());
  4. Add an example in examples/<nome>-example/ with round-trip
  5. Open a PR with a tag new-adapter
