🤖 What a coding agent is (and what it ISN'T)

A coding agent is a LLM that runs an autonomous loop: reads code, plans an action, edits files, runs commands in the terminal, observes the result, and decides the next step — all without you dictating every move. It's not autocomplete or a chatbot. It's an iterative collaborator.

✓ Is a coding agent

  • ✓Carries out a task end to end (read, plan, act, review)
  • ✓Has access to tools (shell, file edit, web, MCP)
  • ✓Maintains session context and iterates
  • ✓You can delegate to specialized sub-agents
  • ✓Runs event hooks (PreToolUse, Stop, etc.)

✗ Is not a coding agent

  • ✗Autocomplete (Copilot inline) — suggests a line
  • ✗Pure chatbot (standard ChatGPT) — no tools
  • ✗Linter/formatter — static rule
  • ✗Snippet expander — fixed template
  • ✗Code search — queries only, takes no action

🔬The ReAct loop (Reason + Act)

It’s the engine behind any coding agent. It runs in short cycles:

1. Observe — read the message, available tools, and context
2. Think — what’s the next action that will bring you closer to the goal?
3. Act — execute the action (read file, run bash, edit, etc.)
4. Observe — action result. Return to step 2 or stop.

📁 .claude/ vs .codex/ vs .agents/ — the anatomy

Hidden folder in the project where the agent customization lives. Claude uses a single folder. Codex uses two folders with separate responsibilities. This is the most important structural difference:

Claude Code — a single folder

.claude/
├── CLAUDE.md            ← também pode ficar na raiz
├── settings.json        ← permissões, modelo, env, hooks
├── settings.local.json  ← override local (.gitignore)
├── agents/              ← sub-agents em Markdown
│   ├── code-reviewer.md
│   └── doc-writer.md
├── skills/              ← skills auto-invocáveis
│   └── my-skill/
│       ├── SKILL.md
│       ├── scripts/
│       └── references/
├── commands/            ← slash commands
│   └── review.md
└── hooks/               ← scripts de evento

Codex — two folders, distinct responsibilities

.codex/                  ← config específica do Codex
├── config.toml          ← settings em TOML
├── agents/              ← sub-agents em TOML
│   ├── code-reviewer.toml
│   └── doc-writer.toml
└── commands/            ← slash commands específicos

.agents/                 ← spec ABERTA (compartilhada)
└── skills/
    └── my-skill/
        ├── SKILL.md
        ├── agents/openai.yaml  ← sidecar Codex
        ├── scripts/
        └── references/

AGENTS.md                ← na raiz, system prompt do projeto

⚠️Migration pitfall #1

People coming from Claude put the skill in .codex/skills/ thinking it’s the direct equivalent of .claude/skills/. Wrong. Codex skill lives in .agents/skills/ — because .agents/ is the convention used by the open Agent Skills spec, and Codex follows it.

🧩 Skills — the shared concept, with small differences

A skill is a "packaged expertise": folder with SKILL.md + YAML frontmatter + Markdown body + conventional folders. Both runtimes implement the Agent Skills standard (agentskills.io), so the core is portable. Where they differ:

The 4 pillars that ALWAYS match

1
File Name SKILL.md — always
2
Frontmatter fields name e description in YAML
3
Body in standard Markdown
4
Folder conventions scripts/, references/, assets/

Minimal SKILL.md

---
name: minha-skill
description: Use when you need to process X. Common triggers: "process X", "clean up Y".
---

# My Skill

Markdown instructions explaining how to perform the task.

You can reference relative files: see `references/exemplo.md` for more details.

🔷 Claude Code adds

  • • allowed-tools in frontmatter
  • • disable-model-invocation (explicit opt-in)
  • • Dynamic injection with `!comando` (backtick-bang)
  • • Automatic invocation by description
  • • Slash: /nome-skill

🟣 Codex adds

  • • Sidecar agents/openai.yaml (branding, MCP)
  • • Hidden ~8K-character limit on description
  • • No native dynamic injection (use fallback prose)
  • • Automatic invocation by description (also)
  • • Dollar: $nome-skill

🦜This is exactly where polyskill comes in

You write ONE skill in the portable format. polyskill generates two versions: one with Claude’s conventions, the other with Codex’s conventions (including the sidecar and description adjustment). See the Track 5 for details.

👥 Sub-agents — two opposing philosophies

A sub-agent is a "specialized persona" that the main agent can delegate tasks. This is where the trickiest difference between Claude Code and Codex lies — it catches almost everyone who migrates:

🔷

Claude Code — automatic invocation

Markdown format in .claude/agents/. The main agent READS the description and decides whether to delegate, on its own.

You write a description rich in triggers ("Use proactively when..."), and the main Claude agent discovers the sub-agent when the context matches. You can run several in parallel via the Task tool.

🟣

Codex — explicit invocation

TOML format in .codex/agents/. You HAVE to call it by name in the prompt.

Description helps you remember, but it doesn’t trigger automatically. “Use the agent code-reviewer to review X” — without that, it won’t run. Trade-off: more predictable, less ergonomic.

🚨The #1 mistake people make when migrating from Claude → Codex

Copy the sub-agent, translate it to TOML, and expect it to run on its own like it does in Claude. Doesn't trigger. You spend hours thinking "it’s broken"—it isn’t. Codex requires explicit invocation by design.

Key concepts

Auto-dispatch
Claude reads the description and decides
Explicit call
Codex requires a name
Isolation
Separate context
Parallelism
Multiple at once

🔌 MCP — the protocol they both speak

Model Context Protocol (MCP) is the common denominator of the stack. An open standard for connecting LLMs to external tools (Slack, Gmail, GitHub, databases). An MCP server runs as an independent process — Claude and Codex speak the same protocol.

The MCP architecture

┌──────────────┐ ┌──────────────┐
│ Claude Code │────┐ │ MCP Server │
└──────────────┘ │ │ (slack-api) │
├──→ │ │
┌──────────────┐ │ │ Exposes tools │
│ Codex CLI │────┘ │ via stdio │
└──────────────┘ └──────────────┘
Both clients use the SAME server.
Server is independent, declared in the client config.

🔷 Declaration in Claude Code

// .mcp.json
{
  "mcpServers": {
    "slack": {
      "command": "npx",
      "args": ["-y", "@mcp/slack"],
      "env": { "TOKEN": "$SLACK_TOKEN" }
    }
  }
}

🟣 Declaration in Codex

# config.toml
[mcp_servers.slack]
command = "npx"
args = ["-y", "@mcp/slack"]

[mcp_servers.slack.env]
TOKEN = "${SLACK_TOKEN}"

💡The good news

Configured an MCP server once? Both runtimes can use it. Only the declaration format changes (JSON×TOML). Server, env, exposed tools — all the same. This is the part of the stack that survives the MOST across runtimes.

Key concepts

Open standard
MCP is a spec, not proprietary
Independent server
Separate process
stdio vs HTTP
Two transports

Naming convention
